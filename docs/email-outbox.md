# Durable email delivery

EmailService methods acknowledge durable queue acceptance, not delivery. Application submission queues its receipt and dispatch alert in the same database transaction. The unique workflow key prevents duplicate emails when submission is retried. Custom/campaign sends intentionally create new jobs.

The `/api/cron/email-outbox` GET endpoint requires `Authorization: Bearer <CRON_SECRET>`. Configure `CRON_SECRET`, `RESEND_API_KEY`, and `EMAIL_FROM` in the deployment environment. The processor handles 25 messages per invocation; it never falls back to simulated delivery when production credentials are missing.

The current Vercel Hobby plan cannot run five-minute cron jobs. `.github/workflows/email-outbox.yml` provides an external five-minute schedule and a manual trigger, using a standard Ubuntu runner with no checkout or third-party actions. The repository was verified public with Actions enabled on 19 October 2026; [standard runners are free for public repositories](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Reassess runner costs before making the repository private. The workflow logs only aggregate counts, fails on HTTP, timeout, malformed responses or delivery failures, and never follows redirects with credentials.

Activation is deliberately opt-in. Publish the workflow to the default branch (`main`), create the `email-outbox` GitHub environment, and configure:

- Environment variable `EMAIL_OUTBOX_ORIGIN`: the exact HTTPS Catchingjobs deployment origin, with no path. Approved hosts are `catchingjobs.co.uk`, `www.catchingjobs.co.uk`, or this project's immutable Vercel deployment hosts.
- Environment secret `EMAIL_OUTBOX_CRON_SECRET`: the same value as the target deployment's `CRON_SECRET`.
- For protected Preview only, environment secret `EMAIL_OUTBOX_PREVIEW_BYPASS_SECRET`: a Vercel automation bypass secret. Leave it absent for a public production endpoint.
- Repository variable `EMAIL_OUTBOX_ENABLED=true`, only after configuring and verifying the target. Delete this variable or set it to `false` to pause both scheduled and manual processing.

Use the manual trigger to validate the staging target with an empty queue first, then a synthetic email addressed only to a provider-controlled test mailbox. Configure the deployment's Resend credentials before this delivery check. Verify the database marks that synthetic job SENT and a second invocation does not resend it. Production activation requires the production schema and credentials, a verified sender, and completed release checks; do not point this workflow at the historical production deployment before those changes are released. [GitHub schedules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) run from the default branch and may be delayed or dropped under load. Public repository schedules are disabled after 60 days without repository activity. This is a best-effort scheduler, not a guaranteed five-minute delivery SLA: monitor the last successful workflow run and oldest queued message, enable GitHub Actions failure notifications, and check that the schedule remains enabled. If guaranteed timing becomes a requirement, move the same authenticated endpoint to a dedicated scheduler with an appropriate service level.

Workers claim rows with an atomic lease, reclaim expired leases after ten minutes, and use a stable provider idempotency key for retries. Failures retry with exponential backoff, up to eight attempts, then enter `FAILED`. Uncertain deliveries older than 23 hours are failed for manual reconciliation, avoiding retries beyond [Resend's 24-hour idempotency retention](https://resend.com/changelog/idempotency-keys). Monitor oldest pending age and FAILED counts in EmailOutbox, plus scheduler failures; inspect EmailLog for delivered provider IDs. Do not expose recipient addresses or rendered messages through public diagnostics.

The additive SQL in `apps/api/prisma/migrations/20261018020000_durable_delivery_and_private_documents/migration.sql` introduces the outbox, private documents, webhook deduplication, and query indexes. No production database migration was run during implementation. Existing installations previously used schema push and have no migration history: back up the database, compare its schema with the pre-change schema, baseline that schema using Prisma's documented existing-database workflow, and apply the additive migration in a preview/staging database before production. Do not run migrate reset against existing data. For disposable fresh development databases, use the full Prisma schema with db push. Generate the client after schema changes.

Deploy the additive schema before API code that queues messages. Configure and validate the processor in preview before production. Roll back application code without dropping these additive tables; pending jobs remain available for the next successful processor run. Failed messages require an authorised operator to fix the cause and explicitly requeue; never mass-requeue SENT jobs.
